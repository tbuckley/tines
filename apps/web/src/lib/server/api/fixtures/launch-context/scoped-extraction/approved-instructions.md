# Approved extraction instructions

Source: Tines/519 `distill-report` v2. These are the approved Distilling v3 and Applying v2 bodies used to review this fixture.

## Distilling v3

You are in the Distilling stage. Goal: prune this project's journals and propose guidance that stays useful without making every run read every procedure.

1. Inventory journals and matching prompt guidance. Use `tines context list -k prompt -p <project> --all-pages --json` for project journals, selecting items named `journal`; also inspect the global, project and state prompt items that apply to this project's workflows. Include inherited/base-state context and identify scopes by workflow/state, not state name alone. `tines journal show|rewrite --state <workflow>/<state> <ref>` reaches another state's journal; a child sharing a root uses that root's journal. Do not repeatedly rewrite the same inherited item.
2. Prune journals directly: merge duplicate bullets while preserving recurrence marks, remove stale or disproven entries, and tighten prose without losing exact operational detail. Verify recurring claims against current commands, source and issue status. If a lesson is a workaround for a tooling defect, find its existing issue or file a bug instead of making the workaround a permanent rule.
3. Separate universal guidance from conditional procedures. Rules that apply to every run at a scope remain inline. Journal bullets or prompt text needed only for some tasks become proposals to move that material into a skill at the exact same scope: global stays global, project stays project, state stays that workflow state, and combined project/state stays that combination. Do not broaden scope or strip qualifiers. Inspect existing skills first and prefer updating a relevant one. A skill's description must explain when an agent should read it; its contents hold the operational detail. Do not add required/reference tags, a packing policy, a token target, or new retrieval tools.
4. Draft exact proposals. For each move, name the source item/version and destination skill name/scope; provide the complete proposed skill files, one-line description, and full replacement inline text. The inline prompt describes the skill in one line, including when to read it and `skills/<name>/SKILL.md`; avoid duplicating a description already supplied by the launch renderer. Preserve material needed on every run, current human instructions, and any explicit required reads unless the proposed replacement changes them for review. A conditional move is not ordinary pruning: leave the source material available until the destination is approved, written and verified. Universal recurring lessons may still be proposed for inline promotion.
5. Attach `distill-report` as text/markdown. Include a concise pruning summary, each proposal's exact before/after text and skill files, the read condition and why it is conditional at this scope, and links to any tooling issues. Use an example task that needs the skill and one that does not. Transition "Propose changes" when proposals exist, or "Nothing to promote" for pruning only.

Do NOT edit shared instructions or create/update shared skills during Distilling. Only journal pruning is direct upkeep. Skill extraction and inline promotions wait for human approval in Proposal Review; do not delete the proposed source text as a shortcut around that approval.

## Applying v2

You are in the Applying stage. The Proposal Review comments authorize you to apply only the approved proposals in the distill-report, including approved skill changes and their matching inline replacements. For those changes, this authorization overrides the general rule against editing shared context directly.

1. Read the distill-report and all Proposal Review comments. Apply the approved list with the human's amendments; skip anything rejected or unmentioned. Read current source and destination versions before writing. Preserve unrelated changes added since the proposal; if an approval no longer resolves a material conflict, leave that move unapplied and explain what needs a decision.
2. For each approved skill extraction, create or update the skill first using existing context commands and the approved files/description. Keep the exact scope; when updating an existing skill, preserve unrelated files. Check current CLI help for the file upload form. Verify the stored files and the effective context for a representative issue at that scope, including the intended `skills/<name>/SKILL.md` path and any same-name override. If the destination cannot be delivered as intended, leave the source text in place and report the problem.
3. Apply the matching approved inline replacement only after the skill is verified. Use `tines context edit <id> --body @file --expect-version <v>` for prompt items and the journal rewrite command with its current version for journals. Keep universal rules inline and one skill discovery line with its read condition/path, without duplicating a line already supplied by the renderer. An interrupted move may temporarily duplicate text; it must not leave the procedure missing from both places. Resume from the verified current versions rather than blindly replaying writes.
4. Verify the resulting effective prompt and skill bundle. A task needing the procedure must be able to discover and read it; unrelated tasks should receive only the discovery line. Confirm the scope and required rules are preserved. For inline-only promotions, use the same version-checked edit and verification path.
5. Comment concisely with the items changed, their resulting versions and any approved change left unapplied with its reason. Transition "Applied" when the approved work is complete; otherwise leave a clear handoff and use the workflow's appropriate available transition.

Do not apply a change that was not approved. Do not remove source material while its skill is unavailable or resolve a material review ambiguity by guessing.
