# Tines

pnpm monorepo (Node >= 20). `apps/web` is a SvelteKit (Svelte 5) app deployed to Cloudflare Workers with D1/Kysely; `packages/cli` and `packages/shared` are the CLI and shared code.

## Layout and conventions

`README.md` has the package table and the setup, deploy, and supervisor/runner detail. What it does not say, and what surrounds those packages:

- `docs/` — how-to guides for jobs you may be handed: running the runner daemon (`runner-daemon.md`), adding a context kind (`adding-a-context-kind.md`), measuring navigation (`PERFORMANCE.md`). Living documents: correct them when they go stale.
- `specs/` — one folder per subsystem holding its design record. These are **historical**: they say what a change set out to do, not what the code does now, and they run ahead of what has shipped. Never edit a spec to match the code — when the two disagree, either fix the code or record the new decision.
- `apps/web/migrations/` — D1 migrations, applied by `wrangler d1 migrations apply` in filename order. Give a new one the next unused number; nothing assigns them, so read the directory first (two concurrent PRs both picking `0010` is how the first duplicate got in). A collision can also arrive from `main` *after* you looked, so `pnpm check` runs `apps/web/scripts/check-migrations.mjs`, which fails on a name that is not `NNNN_snake_case.sql`, on a gap, and on a duplicate — except `0010`, whose pair is grandfathered in the script because both files are already applied under those names in production (so `ls` showing two `0010`s is expected, not a failure the check missed); CI runs it against the PR's merge commit, so a red check is real even when your own tree looks fine — fix it, never merge over it. Fixing means renumbering, and renaming a file D1 has already applied makes it re-run under the new name on preview and production: renumber the file whose every statement is `IF NOT EXISTS` (`CREATE TABLE`/`CREATE INDEX`), never an `ALTER TABLE ADD COLUMN`, which SQLite cannot make idempotent — prefer the safe file over the newer one. Keep them backwards-compatible with the deployed worker — they run before it.
- `scripts/` — repo-wide guards that `pnpm check` runs before the typechecks. `check-package-scripts.mjs` fails on a package.json script whose name is a pnpm command (`deploy`, `publish`, `prune`, …): pnpm's own command wins, so `pnpm <name>` runs that instead of the script and only `pnpm run <name>` reaches it. Suffix such a script (`deploy:prod`) rather than documenting around it. The exceptions are `start`, `test`, `restart` and `install`, which pnpm does run as scripts.
- `apps/web/src/lib/components/ui/` — shadcn-svelte components, generated by `pnpm dlx shadcn-svelte@latest add <name>` against `apps/web/components.json`. Don't hand-write or hand-edit them; wrap them in `apps/web/src/lib/components/` instead.
- `apps/web/e2e/` — the Playwright suite. `pnpm test` does not run it (see `pnpm test:e2e` below); the CI workflow does, on every pull request, so a green unit run alone says nothing about end-to-end behaviour — run it yourself before claiming any.
- `.github/workflows/` — `ci.yml` gates pull requests (typecheck, formatting, unit tests, e2e). `preview.yml` also runs on every pull request from a branch in this repo, and it applies that PR's migrations to the shared `tines-preview` D1 before uploading a preview worker — so a migration is exercised against a real, shared database as soon as the PR opens (README, "PR preview URLs"). Merging to `main` is a release: it deploys the worker to production and publishes a new `tines` to npm. There is no separate release step to forget.

## Commands

- `pnpm dev` — run the web app
- `pnpm build` — build `apps/web` and `packages/cli` (`@tines/shared` has no build step; it is consumed as TypeScript source and bundled by both)
- `pnpm check` — the migration-numbering and package-script-name checks, then typecheck/svelte-check all packages
- `pnpm format` / `pnpm format:check` — Prettier (config in `.prettierrc`; `.prettierignore` skips generated UI components, `specs/`, and Markdown). CI runs the check, so format before pushing.
- `pnpm test` — vitest unit tests
- `pnpm db:migrate:local` / `pnpm db:seed:local` — create the local D1 tables, then a dev user and API key (see the README's Getting started)
- `pnpm test:e2e` — Playwright e2e suite (boots the built worker under `wrangler dev` with a seeded local D1; see `apps/web/e2e/`). Run by `ci.yml` on pull requests, but not by `pnpm test`.
- `pnpm cli <command>` — run the CLI from source against `http://localhost:5173` (the script pins `TINES_API_URL`, so an ambient value is ignored; pass `--url` for any other target). The published CLI defaults to `https://tines.tbuckley.dev`.

## Icons

Use Tabler Icons via `@tabler/icons-svelte`, and always import icons with deep imports rather than the package barrel:

```svelte
<script lang="ts">
	import IconHeart from '@tabler/icons-svelte/icons/heart';
</script>

<IconHeart size={20} stroke={1.5} />
```

Do not use barrel imports (`import { IconHeart } from '@tabler/icons-svelte'`): the barrel re-exports every icon in the package (~6,200 in 3.46.0) plus their aliases, which makes Vite dev-server startup and HMR noticeably slower. Deep import paths are the icon name in kebab-case (e.g. `icons/arrow-left`, `icons/heart-filled`), each exporting the component as its default.
